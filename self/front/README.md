# self/front — 화면

사진 한 장 → 비슷한 장소 후보 카드 → (마음에 드는 곳 고르기) → 출발지(내 위치 또는 역)와 최대 이동시간 고르기 → 채팅 카드에서 조건 입력 → 추천 결과(이동시간 포함).

실제 검색, 이동시간, 챗봇에 연결돼 있다. 연결이 실패하면 더미(예시) 데이터나 대체 답으로 바꿔서 화면이 끊기지 않게 하고,
더미로 대체된 데이터가 화면에 있을 때만 머리글에 **"더미 데이터"** 표시가 나온다.

## 실행

저장소 맨 위 폴더에서 (처음 한 번):

```
python3 -m venv .venv
.venv/bin/python -m pip install -r self/front/requirements.txt
```

실행:

```
cd self/front
../../.venv/bin/streamlit run app.py
```

- `self/front` 안에서 실행해야 `.streamlit/config.toml`(각진 모서리, 흰 바탕, 업로드 10MB 제한)이 적용된다. 채팅 카드와 말풍선의 둥근 모서리는 `style.css` 가 따로 덮어쓴다.
- 처음 검색할 때 사진 검색 모델(`google/siglip-base-patch16-224`, 약 813MB)을 내려받는다. 이후에는 캐시에서 올라온다.
- 서버를 켠 뒤 **첫 검색은 3~7초** 걸린다(모델 로딩). 시연 전에 한 번 돌려 두면 좋다.
- 이 폴더의 코드는 키를 읽지 않는다. 키는 아래 파일들이 `self/.env` 에서 읽는다.

## 필요한 키 (`self/.env`, 이름만. 값은 적지 않는다)

| 이름 | 쓰는 곳 | 없으면 |
|---|---|---|
| `OPENAI_API_KEY` | 챗봇 (`self/embedding_all/travel_chatbot.py`) | 챗봇 대체 답 (사진이 비슷한 상위 3곳) |
| `NAVER_MAPS_CLIENT_ID`, `NAVER_MAPS_CLIENT_SECRET` | 자동차 이동시간 (`self/total/route_tools.py`) | 자동차 이동시간 "이동시간을 불러오지 못했어요" |

| `app.py` | 화면 3단계(사진 올리기 / 후보 보기 / 대화로 추천), 채팅 카드, 출발지 · 최대 이동시간 선택칸, 화면 전환, 기다리는 동안의 처리 순서(`submit` → `process_pending`) |

`self/total/route_tools.py`(길찾기), `shared/place_cards.csv`(장소 정보).

## 화면 구성

| 단계 | 화면 |
|---|---|
| 1. 사진 올리기 | 사진 올리기 또는 "예시 사진으로 해보기" + **출발지**(내 위치 사용 / 가까운 역 6곳 / 선택 안 함)와 **최대 이동시간**(제한 없음 / 1~5시간) 선택칸. "찾기"를 누르면 사진 검색 → 반경 선제외 → 이동시간 조회 → 후보 9곳까지 한 번에 처리한다. 처리 중에는 "비슷한 장소를 찾는 중... → 이동시간을 확인하는 중..."이 보이고 입력과 선택칸이 막힌다 |
| 2. 후보 보기 | 후보 카드 3장씩 두 줄(출발지가 있으면 카드마다 **이동시간**). 카드마다 **이 장소 보기**, 출발지 · **최대 이동시간** 선택칸, 조건 칩, 입력창(본문 안, 칩 아래) |
| 3. 대화로 추천 | 왼쪽: 올린 사진 · 후보 목록 · 출발지와 최대 이동시간 선택. 오른쪽: 둥근 **채팅 카드 "여행 도우미"** |

채팅 카드 (위에서 아래로): 제목줄(출발지 상태) → 스크롤 메시지 영역(높이 `clamp(360px, 60vh, 640px)`, 항상 최신이 아래, 챗봇 말풍선은 왼쪽 · 사용자는 오른쪽, 추천 카드는 챗봇 말풍선 아래) → 빠른 조건 칩 4개 → 입력창.

- **시작 메시지**: "비슷한 곳 N곳을 찾았어요. 마음에 드는 곳을 고르거나 조건을 말해 주세요." (질문 없음)
- **이 장소 보기**: 후보 카드에서 한 곳을 고르면 "선택한 곳" 카드(이름 · 지역 · 이동시간 · 소개글 전체)가 나온다. 챗봇은 부르지 않고, 네이버는 그 장소 1건만 부른다(출발지가 있을 때). 네이버 지도 링크는 URL 형식을 확인하지 못해 만들지 않았다.
- **같은 질문 중복**: 챗봇이 본문과 `question` 에 같은 문장을 쓰면 한 번만 보여 준다(`ui.repeats_sentence`).

## 출발지와 최대 이동시간

**업로드 화면에서도 고른다.** 사진 올리기 옆(왼쪽 열)에 후보 · 대화 화면과 같은 선택칸이 있고, 고른 값은 같은 `session_state`(`origin_query`, `my_location`, `max_hours`, 위젯 키 `origin_choice` · `max_hours_choice`)에 저장돼서 업로드 → 후보 → 대화 화면에서 그대로 쓴다. 내 위치 허용 컴포넌트도 같은 코드(`render_location_button`)다.

- **"찾기" / "예시 사진" → 한 번에**: `request_search` 가 사진을 상태에 두고 `pending={"kind": "search"}` 로 표시한 뒤 다시 그리고, 다음 실행에서 `process_pending` 이 ① 사진 검색(장소 500곳) ② 출발지가 있으면 반경 선제외 + 이동시간 조회로 후보 9곳 ③ 후보 화면으로 이동을 처리한다. 출발지가 **"선택 안 함"** 이면 이전과 같이 유사도 순 앞 9곳으로 시작한다(최대 이동시간만 정해도 출발지가 없으면 적용되지 않는다). 후보 화면에서 출발지 · 시간을 바꾸면 즉시 갱신되는 기존 동작은 그대로다.
- **처리 중**: 사진 올리기 칸, 선택칸 2개, "내 위치 사용", "찾기", "예시 사진", 서비스 이름 버튼이 모두 막힌다. 안내는 출발지가 있으면 "이동시간 확인까지 최대 40초 정도"(실측: 검색 3.1~3.2초, 이동시간 확인 5.9~23.1초를 근거로 한 어림값, 모델을 처음 불러올 때의 최대 시간은 재지 않았다), 없으면 "10초 정도".
- **위치를 묻는 동안** "찾기"와 "예시 사진"은 막힌다(위치가 정해진 뒤에 눌러야 그 위치로 후보를 고른다). 취소하면 다시 활성화된다.
- **처음으로 돌아가면 조건을 모두 지운다**: "다른 사진 올리기"나 서비스 이름 버튼(`start_over`)이 `origin_query`, `my_location`, `max_hours` 와 함께 위젯 키(`origin_choice`, `max_hours_choice`)를 지운다. 선택칸은 이미 그려진 뒤에는 값을 바꿀 수 없어서, 플래그(`clear_widget_keys`)를 두고 다음 실행 맨 앞에서 지운다.
- 검색 중 예상 못 한 오류가 나면 업로드 화면에 "사진을 검색하지 못했어요" 안내만 보이고 대기가 풀린다.

- **출발지**: **"내 위치 사용"** 버튼 + 아래의 "또는 가까운 역" 선택칸(미리 정한 역 6곳 또는 "선택하지 않음"). 역 선택은 위치를 못 가져올 때 쓰는 대체 수단으로 그대로 둔다.
- **최대 이동시간**: 출발지 옆 선택칸(제한 없음 / 1 / 2 / 3 / 4 / 5시간, 기본 **제한 없음**). 후보 화면과 대화 화면이 같은 값(`state.max_hours`)을 쓴다. 창이 1250px 이하로 좁으면 두 선택칸이 위아래로 쌓인다.
- 칩 **"2시간 안에 갈 수 있는 곳"** 은 최대 이동시간을 2시간으로 정하고 그 문장을 질문으로 보낸다. 선택칸 값은 다음 실행 맨 앞(`app.py` 맨 아래 `max_hours_apply`)에서 바뀐다. 이미 그려진 선택칸의 값은 같은 실행에서 바꿀 수 없기 때문이다.
- **출발지가 있고 최대 이동시간이 정해졌을 때만** 아래 "후보 거르기"가 동작한다. 출발지가 없으면 제한은 적용되지 않고 선택칸 아래에 "최대 이동시간은 출발지를 고르면 적용돼요."가 보인다.

### 조건을 정하면 바로 후보가 바뀐다 (질문을 보내지 않아도)

내 위치 성공 · 출발지 변경 · 최대 이동시간 변경이 일어나면(후보 화면 · 대화 화면 모두) 곧바로 후보를 다시 고른다. 챗봇(OpenAI)은 부르지 않는다.

| 선택 | 하는 일 | 화면 |
|---|---|---|
| 출발지 없음 | 처음 후보 9곳으로 되돌림, 이동시간 없음 | 처음 모양 |
| 출발지만 (제한 없음) | **보이는 후보 9곳**의 자동차 이동시간만 조회 | 카드와 왼쪽 목록에 이동시간 |
| 출발지 + 최대 이동시간 | "후보 거르기"(반경 밖 제외 → 남은 곳 중 상위 50곳 병렬 조회 → 부족하면 10곳 더, 최대 60곳)로 제한 이내인 **최대 9곳** | 카드와 왼쪽 "조건에 맞는 후보" 목록이 그 9곳으로 바뀌고 이동시간 표시, 제목 "서울역에서 2시간 이내 장소 N곳" |
| 채택 0곳 | 카드 대신 "조건에 맞는 곳이 없어요(확인한 N곳). 최대 이동시간을 늘려 보세요." | 후보 화면 · 대화 화면 왼쪽 모두 |

- **처리 중**: 기존 `pending` 구조(`{"kind": "refresh"}`)를 재사용한다. "조건에 맞는 곳을 찾는 중..."(제한 없이 출발지만이면 "이동시간을 계산하는 중...")이 보이고, 선택칸 · 내 위치 · 조건 칩 · 입력창 · "이 장소 보기" · "다른 사진 올리기"가 모두 막힌다. 안내는 "최대 30초 정도". 근거: 후보 50건 조회가 5.9초, 9.7초, 23.1초 걸렸다(실측, 요청 1건 평균 0.45~0.86초로 네이버 응답 속도에 따라 크게 달랐다). 60건까지 가는 경우와 더 느린 응답은 확인하지 못했다(미확인).
- **마지막 선택만 반영**: 처리는 "처리 시작 시점의 선택"(`current_sig()` = 출발 좌표 + 최대 이동시간)으로 하고, 이미 같은 선택이 반영돼 있으면(`applied_sig`) 건너뛴다. 처리가 끝나기 전에 여러 번 바꿔도 끝난 뒤 한 번만 처리하고, 같은 요청은 1시간 캐시라 네이버를 다시 부르지 않는다. 다만 처리가 시작된 뒤에는 컨트롤이 막혀서(브라우저 반응 약 0.1초) 사실상 연속 변경은 들어갈 수 없다.
- **일관성**: 고른 결과는 `state.selection`(선택 서명 + 결과)에 두고, 질문을 보낼 때 **같은 (출발지, 제한)이면 다시 조회하지 않고 그 결과를 그대로 쓴다**. 그래서 후보 카드, 챗봇 입력(후보와 이동시간), 추천 카드가 서로 어긋나지 않는다. 더미 답도 같은 값을 쓴다. 질문으로 선택이 바뀌는 칩("2시간 안에 갈 수 있는 곳")은 질문 처리 안에서 후보를 먼저 한 번 고른 뒤 같은 결과로 답한다.
- **멈춤과 재시도**: 일시적 오류로 조회가 중간에 멈추면 "이동시간 조회가 중간에 멈췄어요(확인한 N곳)" 안내를 보이고, 다음 질문 때 못 구한 후보만 한 번 더 시도한다(실패한 요청은 60초 동안 다시 보내지 않음). **429(속도 제한)** 가 나면 즉시 멈추고, 그 뒤 60초 동안은 모든 곳에 새 요청을 보내지 않으며(캐시 값만 사용), 자동으로 다시 시도하지 않는다. 인증 오류(401, 403)도 자동으로 다시 시도하지 않는다.
- 대화창에 "3시간 안에" 처럼 직접 쓴 문장은 선택칸에 반영되지 않는다(칩만 연결). 선택칸이 기준이다.

### 내 위치 사용

1. **"내 위치 사용"** 을 누르면 그때만 브라우저에 위치를 묻는다(허용 여부는 브라우저가 사용자에게 묻는다). 허용하면 출발지가 **"내 위치"** 로 바뀌고(선택칸 표시, 채팅 카드 제목줄 "출발지 내 위치"), 선택칸에 "내 위치" 항목이 생겨서 역으로 바꿨다가 다시 고를 수 있다. 후보 화면과 대화 화면이 같은 출발지를 쓴다.
2. 거부 · 시간 초과(약 12초) · 위치를 알 수 없음 · 브라우저가 지원하지 않음 · **한국 밖 좌표**(`route_tools.is_valid_coordinate` 기준) · 이상한 값이면 **오류 화면 없이** "위치를 가져오지 못했어요. 아래에서 가까운 역을 골라 주세요"만 보이고 역 선택으로 계속 진행한다. 위치를 묻는 동안에는 "취소"를 누를 수 있다.
3. 좌표는 **소수점 3자리(약 100m)로 반올림**한다(브라우저에서 한 번, Python 에서 한 번). 그 값이 이동시간 캐시 키이자 네이버 출발 좌표라서, 같은 동네에서는 이전에 구한 이동시간을 다시 쓴다.
4. 출발지(내 위치 · 역)가 바뀌면 출발 좌표가 달라서 캐시 키가 달라진다. 이전 출발지의 이동시간이 새 질문에 섞이지 않는다. "다른 사진 올리기"나 서비스 이름 버튼으로 처음으로 돌아가면 위치와 출발지 · 최대 이동시간 선택(위젯 포함)이 모두 지워진다.
5. **위치 좌표는 이 화면의 세션(메모리) 안에서만 쓴다.** 로그 · 파일 · 저장소에 남기지 않고, 챗봇(OpenAI)에도 좌표 없이 이름("내 위치")만 보낸다. 네이버에는 출발 좌표로만 넘어간다. 서버 코드(`backend.py`)는 위치를 모듈 변수에 두지 않는다(세션이 섞이지 않게 `app.py` 의 화면 세션이 갖는다).
6. **받는 방식**: 서드파티 패키지(예: streamlit-geolocation) 없이, Streamlit 이 주는 `components.v1.declare_component` 와 약 30줄의 JavaScript(`ui.LOCATION_COMPONENT_HTML`)로 만들었다. 이 코드는 시작할 때 임시 폴더의 `index.html` 로 저장된다(고정된 코드뿐, 위치 값 없음). `navigator.geolocation` 으로 한 번만 묻고, 반올림한 위도 · 경도와 상태만 부모 화면(같은 출처)에 보낸다. 네트워크 요청, 저장(localStorage, 쿠키), 로그, 정확도 값 전달은 없다. `requirements.txt` 는 바뀌지 않았다.
7. 브라우저는 **https 또는 localhost** 에서만 위치를 준다. 시연을 `http://<내 컴퓨터 IP>:8501` 같은 주소로 하면 위치를 못 받고 안내 문구가 나온다(역 선택으로 진행).

### 후보 거르기 (`travel_tools.select_by_travel_time`)

**흐름: 사진 1,500장 → 장소 500곳 → 직선거리 반경 170km(2시간) 밖 제외 → 남은 곳 중 유사도 상위 50곳 조회 → 제한 이내인 곳 최대 9곳**

1. 첫 검색에서 사진 유사도 순으로 장소 **60곳**(`app.POOL_SIZE`)을 모아 둔다(`state.pool`). 후보 화면에는 앞 9곳(`app.TOP_K`)만 보인다. 장소 500곳을 모으려고 사진을 **1,500장**(`search_tools.PHOTO_TOP_K`) 검색한다(측정: 사진 200장 → 장소 약 131곳, 1,000장 → 500곳). 검색 시간은 사진 수와 거의 상관없다(200장 0.057초, 1,500장 0.059초, 모델 로딩 제외). 세션당 메모리는 약 560KB.
2. **직선거리 반경 선제외**: 반경(km) = 최대 이동시간(시간) × `PREFILTER_KMH`(**85**). 2시간이면 170km, 1시간이면 85km, 3시간이면 255km. 반경 밖 장소는 이동시간을 조회하지 않고 뺀다(`excluded`, `radius_km` 가 결과에 남고 `last_status["scan"]` 에도 "반경 170km 밖 N곳 제외"로 보인다). 좌표가 이상한 곳도 뺀다. 출발지 없음 · 최대 이동시간 없음일 때는 쓰지 않는다. `PREFILTER_KMH = None` 으로 바꾸면 끈다.
   - **근거(실호출 실험, 서울역 · 부산역 각 60곳, 직선 50~400km)**: 관측 최대 직선 속도 **72.6 km/h** × 1.15(여유) ≒ 83.5 → 85. 150km · 200km 반경 모두 "반경 밖인데 120분 이내인 곳"은 0곳이었고, 120분 이내였던 곳은 직선거리 최대 101km 였다. 직선이 가까울수록 느리다(50~100km 에서 30~48 km/h).
   - **한계**: 출발지 두 곳, 사진 한 장, 한 시점의 측정이다. 강릉 · 광주송정 같은 다른 출발지나 섬이 많은 지역, 교통이 한산한 시간대는 확인하지 않았다(미확인). 이전에는 "오차가 커서" 직선거리로 거르지 않았는데, 이 실험으로 그 결정을 다시 정했다.
2-1. 남은 곳 중 사진 유사도 순 앞 **50곳**(`SCAN_PLACE_COUNT`)의 자동차 이동시간을 네이버로 **동시에 4건씩**(`MAX_PARALLEL_CALLS`) 조회한다.
3. 제한 이내인 곳만 채택하고, 유사도 순 앞 9곳(`CHATBOT_CANDIDATE_COUNT`, 화면 후보 수 `app.TOP_K` 와 같아야 한다)을 챗봇에 보낸다.
4. 채택이 **3곳 미만**(`MIN_ADOPTED_PLACES`)이면 다음 곳(`SCAN_EXTRA_COUNT` 20 이지만 합계 상한 때문에 실제로는 **최대 10곳**)을 더 조회한다. 조회는 모두 합쳐 **60곳**(`MAX_TRAVEL_CALLS`)까지이고, 그래도 부족하면 그대로 진행한다. 추가 조회도 반경 안 장소에서만 한다.
5. 채택이 **0곳**이면 유사도 상위 9곳을 보내되, 챗봇 입력에 "조건에 맞는 곳이 없었다"고 적는다. 대체 답에도 같은 안내가 나온다. 반경 밖으로 뺀 곳이 있으면 화면 안내에 "(확인한 N곳, 반경 밖 M곳 제외)"가 붙고(반경 안이 0곳이면 "확인한 0곳, 반경 밖 M곳 제외"), 챗봇 입력에도 뺀 곳 수를 알린다.
6. **멈춤**: 일시적 오류(타임아웃, 연결, 5xx), **429**(속도 제한), 인증 오류(401, 403)가 나면 새 요청을 보내지 않고 지금까지 구한 값으로 진행한다. 이미 보낸 요청은 끝까지 기다린다. 이유는 `last_status["scan_stop"]` 에 `transient` / `rate_limit` / `auth` 로 남는다. 멈춘 탓에 0곳이면 "없다"고 단정하지 않고 "조건을 확인하지 못했다"고 챗봇에 알린다.
7. 한 번 구한 이동시간은 챗봇 입력과 추천 카드에 **그대로 쓴다**(다시 부르지 않는다). 같은 (출발지, 장소)는 1시간 캐시(`st.cache_data`, 스레드에서 써도 된다는 것을 확인했다)라서, 제한만 바꿔 다시 물으면 네이버 요청이 0건이다. 출발지가 바뀌면 키가 달라서 이전 값이 섞이지 않는다.
8. 429 감지는 `route_tools` 가 오류를 `DrivingTimeError` 로 바꿔 던질 때 남는 원래 오류(`__context__`)의 상태 코드를 읽는 방식이다(route_tools 는 수정하지 않았다). 읽지 못하면 일반 실패로 본다.

## 로딩 구조 (기다리는 동안)

Streamlit 은 위에서 아래로 다시 실행되는 방식이라 "먼저 그리고, 다음 실행에서 처리"하는 두 단계로 만들었다.

1. 입력 · 칩 · "이 장소 보기" → `submit()` / `pick()` 이 `messages` 에 **내 말을 넣고** `pending` 에 요청을 적은 뒤 바로 `st.rerun()`. 내 말풍선이 즉시 보인다. (업로드 화면의 "찾기" · "예시 사진"은 `request_search` 가 같은 방식으로 `pending={"kind": "search"}` 를 적는다)
2. 다음 실행에서 `process_pending()` 이 챗봇 자리에 **"입력 중" 말풍선**(점 세 개 + 문구)을 그리고 `backend.recommend()` / `describe_place()` 를 부른다. (질문 없이 후보만 바꾸는 `refresh` 는 후보 화면에서는 카드 위, 대화 화면에서는 채팅 카드 안에 같은 말풍선을 보이고, 대화에는 아무것도 추가하지 않는다.)
   - 문구는 실제 단계에 맞게 바뀐다 (`progress` 콜백, `chat_tools` 가 호출): "이동시간을 계산하는 중..." → "추천을 고르는 중...". 최대 이동시간 조건이 있으면 "조건에 맞는 곳을 찾는 중..." → "추천을 고르는 중...". 출발지가 없으면 "추천을 고르는 중..."만.
   - 안내: "이동시간 계산 → 추천 고르기, 최대 50초 정도 걸려요" (실호출 18~31초 기준 어림값. 챗봇 응답만 15.6~26.4초). 최대 이동시간 조건일 때도 같은 "최대 50초". 후보를 50곳 조회 + 9곳 전달로 늘린 뒤의 시간은 **실호출로 재지 않았다**(미확인): 조회는 약 8~10초로 계산했고 챗봇 입력은 약 +25~33% 늘 것으로 어림했다.
3. 처리 중에는 입력창 · 칩 · 출발지와 최대 이동시간 선택 · "후보 카드 다시 보기" · 서비스 이름 버튼이 막힌다.
4. 답을 `messages` 에 넣고 `pending` 을 비운 뒤 `st.rerun()`. **어떤 답이 와도**(오류, 모양이 이상한 답, `None`) 안내 말풍선으로 바꿔서 `pending` 을 반드시 비운다. 그래서 상단 "답변 준비 중..."과 입력창 막힘이 남지 않는다. (화면 실행이 중간에 끊긴 경우에만 `pending` 이 남아 다음 실행에서 이어서 처리한다.)

화면 전환 때 이전 단계 화면이 흐리게 남지 않도록, 단계마다 자리를 고정해 두고(현재 단계는 `st.container()`, 나머지는 `st.empty()`) 현재 단계만 그린다.
처리 중 브라우저를 새로고침하면 `pending` 이 남아 같은 요청이 다시 처리될 수 있다.

## 데이터 흐름

1. **사진** → `search_places`: 사진 단위 결과 1,500장을 장소 단위로 묶어 상위 500곳(`state.pool`) 중 앞 9곳 → 후보. 후보에는 CSV 에서 좌표와 사진 주소를 붙인다.
2. **출발지 · 최대 이동시간**: 후보 화면과 대화 화면 어디서든 고른다. 고르면 질문 없이 바로 후보를 다시 고르고 이동시간을 보여 준다(`backend.refresh_candidates`, 위 "조건을 정하면 바로 후보가 바뀐다").
3. **대화** → `recommend`(조건을 말했을 때) 또는 `describe_place`("이 장소 보기"): 2번에서 고른 후보와 이동시간(`selection`)을 그대로 챗봇에 보낸다. 다시 조회하지 않는다(선택이 아직 반영 전이면 질문 처리 안에서 먼저 한 번 고른다).
   후보 9곳 + 이동시간을 챗봇(`gpt-5-mini`)에 보내고, JSON 답을 읽어 추천을 만든다. 추천 수는 사용자 요청에 맞춰 챗봇이 정하고("가장 ~한 곳"이면 1곳, 말하지 않으면 보통 2~3곳), 최대 **5곳**(`chat_tools.MAX_RECOMMENDATIONS`)까지만 쓴다. 챗봇을 못 불렀을 때의 대체 답은 따로 **3곳**(`FALLBACK_COUNT`)이다.
   챗봇이 고른 `place_id` 가 후보에 없으면 그 추천은 버린다.

## 화면이 받는 데이터

후보 1개 (`backend.search_places()` 가 돌려주는 list 의 원소):

| 키 | 없을 때 화면 |
|---|---|
| `place_id`, `name` | 필수 |
| `region` | "지역 정보 없음" |
| `similarity` (0~1) | 유사도 표시를 숨김 |
| `image_url` | 회색 칸 + "사진을 불러오지 못했어요" (주소가 있는데 안 열리면 단색 칸에 같은 문구) |
| `overview` | "소개글 준비 중". HTML 태그 · 줄바꿈은 걷어내고 한 줄로 자른다 |
| `latitude`, `longitude` | 화면에서는 쓰지 않는다 (이동시간 계산에 쓴다). 범위 밖이면 이동시간만 생략한다 |
| `data_source` | `real` 또는 `dummy`. `dummy` 이면 머리글에 "더미 데이터" 표시 |

추천 답 (`backend.recommend()`): `text`, `recommendations`(`place_id`, `reason`, 이동시간 키들), `question`, `data_source`(`real` / `fallback` / `dummy`).
추천의 `place_id` 는 후보 목록 안에 있어야 그려진다.

### 이동시간 표시 (`ui.travel_line`)

| 상황 | 화면 |
|---|---|
| 자동차, 네이버 값 | `차로 약 7분 · 1.7km` (10km 이상은 `62km`) |
| 도보 (직선 3km 이내) | `도보 약 29분 (추정)` |
| 자동차 값을 못 구함 | 작은 회색 글씨 `이동시간을 불러오지 못했어요` (도보가 있으면 그 줄은 그대로) |
| 출발지 없음, 좌표가 비정상 | 이동시간 줄 없음 |

자동차 이동시간은 **직선거리 추정으로 대체하지 않는다**. 가까운 도심에서 추정이 실제보다 크게 짧게 나왔기 때문이다(서울역→봉화산: 네이버 약 46분, 추정 약 12분).

## 연결이 실패하면

| 상황 | 동작 |
|---|---|
| 검색 모델 없음, 검색 오류 | 더미 후보 6곳 (머리글에 "더미 데이터") |
| 챗봇 키 없음, 타임아웃(60초), 인증, 한도 초과, 서버 오류, 빈 답 | 사진이 비슷한 상위 3곳 + 이동시간, "챗봇을 불러오지 못해서…" 안내 (재시도 없음) |
| 챗봇이 JSON 이 아닌 글로 답함 | 글만 표시, 추천 카드 없음 |
| 네이버 실패 | 일시적 오류(타임아웃, 연결, 5xx)만 최대 2번 재시도, 전체 약 12초 안에 끝. 끝내 실패하면 값 없음. 같은 요청은 60초 동안 다시 보내지 않음 |
| 네이버가 일시적 오류로 실패 | 같은 추천 묶음의 나머지 장소는 호출하지 않음 (다음 메시지에서 다시 시도) |
| 예상 못 한 오류 | 더미 답 |

- 내부 상태는 `backend.last_status` 에 남는다 (`search`, `travel`, `chat`, `chat_chars`, `chat_dropped`, `scan`, `scan_stop`). `scan` 은 "조회 50곳(네이버 요청 50건) / 채택 3곳 / 8초" (예시) 처럼 요약이고(장소 이름 · 좌표는 담지 않는다), 안 했으면 "미사용".
- **끄는 스위치**: `backend.py` 의 `USE_CHATBOT = False` 로 바꾸면 항상 더미 답을 쓴다 (시연 중 챗봇에 문제가 있을 때). 네이버만 끄는 스위치는 따로 없다(키를 비우면 자동차 이동시간만 "불러오지 못했어요").
- `last_status["chat"]` 값: `openai (json_schema)` 정상 / `openai (json_prompt)` · `openai (text_only)` 형식 문제 / `fallback (오류 종류)` 대체 답 / `dummy (…)` 더미 답 / `미사용`.

## 지키는 것

- 사진은 `image_url` 원본 주소로만 보여 준다. 이 폴더에 사진 파일을 두지 않는다.
- 올린 사진은 임시 파일로 잠깐 저장해서 검색하고 바로 지운다. 화면에는 메모리(bytes)로만 있다.
- 내 위치 좌표는 화면 세션 안에서만 쓰고, 로그 · 파일 · 저장소에 남기지 않는다(위 "내 위치 사용").
- 장소 정보와 사진 출처는 한국관광공사 TourAPI (공공누리 제1유형).
- 키 값은 어디에도 출력하거나 저장하지 않는다. 챗봇에 보내는 글자 수만 숫자로 기록한다.

## 알려진 제한 · 확인되지 않은 것

- "내 위치 사용"은 Chrome(헤드리스, 가짜 위치)에서만 확인했다. 실제 기기의 GPS 정확도, 위치 허용 창을 사람이 누르는 흐름, Safari · Firefox · 모바일, https 배포는 확인하지 않았다. 약 100m 반올림은 도시 안에서는 충분하지만 이동시간이 짧은 곳(수 분)에서는 오차가 될 수 있다.
- 반경 선제외 `PREFILTER_KMH=85`는 서울역 · 부산역 한 시점의 측정에서 정한 값이다(미확인: 다른 출발지 · 시간대). 후보 거르기의 50곳 · 3곳 · 추가 10곳 · 상한 60곳 · 동시 4건, 후보 9곳, 이동시간 안내 "최대 50초"는 **제안값이다**(후보 폭을 넓힌 뒤의 실호출 시간은 재지 않았다, 미확인). 동시 4건이 네이버의 속도 제한에 안전한지는 확인하지 못했다(1회에서 429 없음).
- 챗봇 타임아웃 60초, 네이버 타임아웃 5초 · 재시도 2번 · 전체 12초, 대기 60초, 도보 3km 기준, 우회 계수 1.3, 속도 4km/h 는 모두 **근거 없는 제안값**이다.
- 출발지 좌표는 위키백과 좌표(역 대표 좌표)이며 공식 지도와 직접 대조하지 않았다.
- `shared/place_cards.csv` 의 `담양호`(place_id 126323)는 좌표가 한국 범위 밖이다. 고치지 않았고, 이동시간 줄만 생략된다.
- 네이버 호출 한도, OpenAI 비용 한도는 확인하지 않았다. 챗봇은 한 번에 약 3,500자(토큰 약 2,300개)를 보낸다.
- 챗봇이 이동시간 값을 항상 정확히 쓰는지는 실호출 몇 번으로만 확인했다. 질문 규칙을 바꾼 뒤에는 실호출 1턴만 확인했다(질문 0개).
- 화면은 Chrome 에서만 직접 확인했다. Safari · Firefox · 모바일 · 화면 읽기 프로그램은 확인하지 않았다.
- 메시지 영역은 일반 순서(위 → 아래)로 쌓고, 새 메시지가 오면 작은 스크립트(`ui.PIN_TO_BOTTOM_HTML`, 같은 출처 iframe)가 맨 아래로 스크롤한다. 그 스크립트가 막히면(브라우저 설정 등) 맨 위부터 보여서 사용자가 직접 내려야 한다.
- "이 장소 보기"는 후보 화면에서만 된다. 대화 화면 왼쪽 후보 목록은 일반 목록이다.

## 화면 깨짐(Safari)과 챗봇 답 정리

- **제목줄과 메시지 영역이 겹치던 문제**: Streamlit 이 마크다운 상자에 `margin-bottom: -16px` 를 줘서 제목줄(55px)을 담는 상자가 39px 로 계산됐고, 메시지 영역이 제목줄을 16px 덮었다. 스크롤로 올라간 말풍선(갈색)의 아랫부분이 제목줄 쪽에 막대처럼 보이고 말풍선이 제목줄에 붙어 잘려 보였다(Chrome · Safari 모두). 채팅 카드 안에서만 이 음수 여백을 0 으로 되돌렸다.
- **거꾸로 쌓기(`column-reverse`)를 그만뒀다**: Safari(WebKit)는 거꾸로 쌓은 영역의 스크롤 위치(`scrollTop` 음수)를 다르게 다뤄서 맨 아래에서 수십 px 어긋났다(위 여백이 잘리고 아래 카드가 잘림). 일반 순서 + 새 메시지 때 맨 아래로 스크롤로 바꿨다.
- 제목줄 경계에 부드러운 안쪽 그림자, 추천 카드가 있는 답은 말풍선도 카드와 같은 폭(`tf-say--cards`).
- **챗봇 답 정리**(`ui.strip_place_ids`, `ui.bubble_html`): 본문과 추천 이유에서 `place_id: 123`, `(place_id=123)` 같은 번호를 지우고(지운 자리의 쉼표 · 목록 기호 정리), `- 이름: … - 지역: …` 처럼 한 문단에 이어진 " - " 목록은 줄바꿈 목록으로 보여 준다(하이픈이 둘 이상일 때만. "서울 - 부산" 같은 보통 문장은 그대로).
- 확인: 시스템 WebKit(`WKWebView`, Safari 와 같은 엔진)에서 겹침 0px, 맨 아래 고정, 후보 갱신 흐름을 확인했다. Safari 앱 자체, iOS Safari, 오래된 Safari 는 확인하지 않았다.

## 챗봇 입력과 답 규칙 (추천 개수 · 이전 설명 반복)

- **GPT에 가는 입력**: `instructions`=프롬프트(`travel_chatbot.TRAVEL_PROMPT`, 규칙 1~18), `input`=[이전 대화(최근 6개)…, 마지막 user 메시지]. **후보 목록은 마지막 user 메시지에만** 들어가고(`[후보 목록]` … `[사용자 요청]`), 이전 메시지에는 붙지 않는다. 형식은 `travel_reply` JSON(strict): `text`, `recommendations[{place_id, reason}]`, `question`.
- **추천 개수**(예전에는 "최대 3곳"으로 고정): 프롬프트 7번이 "수를 말하면 그 수만큼, 말하지 않으면 보통 2~3곳, 최대 5곳", 스키마 설명과 `MAX_RECOMMENDATIONS=5` 가 같은 값이다. 스키마에 `minItems`/`maxItems` 는 쓰지 않는다(`gpt-5-mini` strict 모드에서 지원되는지 확인하지 못했다, 미확인).
- **직접 답 · 반복 금지**: 16번 "질문에 먼저 직접 답하고, 하나를 골라 달라면 '가장 ~한 곳은 ○○입니다' 한 문장으로 답하고 이유는 `reason` 에, 이미 한 설명은 반복하지 않는다", 17번 "'이 후보'는 직전 답변의 '추천:' 목록".
- **본문에는 이름 · 지역 · 이동시간을 나열하지 않는다**(카드에 표시됨): 14번을 "답변 본문에 장소의 이름 · 지역 · 이동시간을 나열하지 마세요(카드에 표시됩니다)"로 바꿨다 (예전 14번은 "이름, 지역, 이동시간만 짧은 문장으로 소개"여서 스키마 `text` 설명과 충돌했다). 하나를 골라 달라는 질문에는 16번이 "가장 ~한 곳은 ○○입니다" 한 문장으로 답하게 한다. 대화 기록에는 `추천: 이름(이유 30자)` 가 따로 들어가므로 본문에 이름이 없어도 17번("이 후보")의 대상이 유지된다.
- **본문과 카드 이유 중복 방지**: 7번에 "장소별 이유는 `recommendations` 의 `reason` 에만 쓰고 본문(`text`)에는 다시 쓰지 않는다"를 더했고, 18번 "본문은 한두 문장, 끝에 되묻기 · 제안 문장 금지"를 새로 붙였다. 스키마 `text` 설명도 "한두 문장, 장소의 이름 · 지역 · 이동시간 · 이유는 나열하지 않는다(카드에 표시됨), 하나를 고르면 '가장 ~한 곳은 ○○입니다' 한 문장"이다. (이유: 규칙 16을 처음 넣었을 때 실호출에서 본문이 483자로 늘고 같은 이유가 본문과 카드에 두 번 나왔고 끝에 되묻기 문장이 붙었다.)
- **대화 기록에 이전 추천 이유**: 이전 챗봇 답은 `text` + `추천: 이름(이유 앞 30자), …` + `question` 으로 보낸다(`HISTORY_REASON_CHARS=30`, 입력 토큰 절약). 이유가 없으면 이름만 보낸다. 이동시간 값과 `place_id` 번호는 보내지 않는다.
- 규칙 7이 예전에는 "장소 이름, place_id, 이유를 설명하세요"여서 규칙 14(place_id 금지)와 모순이었다. 7번을 "place_id 는 쓰지 마세요"로 고쳤다.
